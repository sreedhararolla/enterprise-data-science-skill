# Experiment Mode: autonomous optimization loop

Experiment Mode runs many propose → run → measure → keep/revert cycles without a human in
the loop, like Karpathy's *autoresearch*, but with the protections an enterprise needs:
noise-aware decisions, locked evaluation, guardrails, budgets, and a one-time holdout.

## 1. When to use it

Use it when all three of these hold:
- There is **one scalar metric** to optimize, with a direction (e.g., validation PR-AUC, WAPE, latency).
- There is a **harness**: a single command that trains and evaluates a candidate and prints the metric, within a bounded time.
- Candidates can be generated by **editing a well-defined surface** (a feature file, a model config, `train.py`).

If the goal is to *understand* something ("why did churn rise?", "what drives NPS?"),
use `research-mode.md` instead. If the metric or validation scheme is not settled yet, do
Phases 0–2 of SKILL.md first. An autonomous loop pointed at the wrong metric just
produces the wrong answer faster.

## 2. The charter: agree once, then run unattended

Fill in `assets/program_template.md` with the user, the way autoresearch uses
`program.md`. It defines:
- the objective and success bar
- the metric and the validation scheme
- the **editable** surface and the **locked** surface
- the time box for each run
- the total budget (runs, hours, and money: GPU hours, warehouse scan cost)
- guardrails
- allowed and forbidden actions
- stop conditions

Once it is agreed, **don't ask the human about anything the charter covers.** Keep going
until a stop condition is hit. **Do stop and ask** before anything outside it: new data
access, spending beyond the budget, installing packages, touching production systems,
sending data to external services, or changing the metric or validation scheme.

## 3. Setup

1. **Branch:** `git checkout -b exp/<yyyymmdd>-<slug>`. Every candidate is one commit, so
   reverting is always a single `git reset --hard <best>`.
2. **Harness:** write `run_experiment.py` (or check the existing one) so that it:
   - runs K seeds or folds (3 is typical; 1 if runs are expensive and the noise is already known)
   - enforces the time box internally, and exits non-zero on failure
   - prints one JSON line: `{"metric": ..., "std": ..., "latency_ms": ..., "fairness_gap": ...}`
   - never touches the holdout.

   Keep the harness deterministic: set seeds, pin library versions, and use a fixed data snapshot.
3. **Measure the noise:** run the unchanged baseline over 3–5 seeds. Set `min_delta` to
   about 1–2 times the seed std, or to the smallest gain that matters to the business if
   that is larger. Without this step, the loop keeps changes that are just seed luck.
4. **Initialize the lab book** (the state file), locking everything the agent must not
   change:

   ```bash
   python scripts/labbook.py init --mode experiment \
     --objective "Churn model: maximize PR-AUC on 2026-Q2 temporal validation" \
     --metric pr_auc --direction max --min-delta 0.004 \
     --budget-runs 80 --budget-hours 10 --patience 12 \
     --guardrail "latency_ms<=50" --guardrail "fairness_gap<=0.05" \
     --lock evaluate.py --lock data/prepare.py --lock data/valid.parquet \
     --holdout data/holdout_2026q3.parquet
   python scripts/labbook.py log --desc "baseline: logistic regression, current features" --metric 0.412 --std 0.003 --commit $(git rev-parse --short HEAD) --extra latency_ms=4 fairness_gap=0.02
   ```

5. **Seed the idea backlog** from the brief, EDA findings, error analysis, and method
   scouting (§5): `labbook.py idea add "recency x frequency interaction" --priority 4`.

## 4. The loop

Repeat until a stop condition is hit:

1. **Read the state:** run `python scripts/labbook.py state`. It is about 30 lines and
   contains the best result, recent runs, rejected ideas, top open ideas, budget, and lock
   status. Rely on it instead of re-reading logs or old outputs; it keeps each
   iteration's context small, however long the session runs.
2. **Choose one change** using the search policy (§5). Write it as a one-line hypothesis:
   *"Adding 90-day spend trend will lift PR-AUC because the error analysis showed
   declining spenders being missed."*
3. **Make one atomic change,** then commit. If you change two things at once, you won't
   know which one helped.
4. **Run the harness** with a hard timeout of about 2 times the time box.
5. **Log it:** `labbook.py log --desc "<hypothesis>" --metric M --std S --commit <sha>
   --complexity simpler|same|more --extra latency_ms=.. fairness_gap=..`
6. **Follow the decision.** On KEEP, stay on this commit. On DISCARD, run
   `git reset --hard <best commit>`. On CRASH, see §7.
   The rule: an improvement must exceed max(min_delta, the combined seed std). A change
   marked `--complexity more` must clear twice that bar. A change marked `simpler` is
   kept if it is within noise of the best, because removing code while holding
   performance is a real win.
7. **Every ~10 runs, consolidate.** Write `labbook.py note "..."` recording what is
   working, what is dead, and where the next gains probably are. Update the idea
   priorities. After any batch of feature changes, run `leakage_scan.py` on the modeling
   table.

Override a decision (`--decision keep --reason ...`) only for a stated reason, such as
a change needed for maintainability. The override is recorded in the lab book.

## 5. Search policy: what to try next

**Expected value by layer.** On enterprise tabular problems, most of the gain usually
comes from the top of this list:
1. **Data and label fixes:** label definition, deduplication, point-in-time corrections,
   filtering bad rows out of training (never out of validation).
2. **Features:** recency, frequency, and monetary features; trends and deltas; ratios;
   time since last event; entity aggregates; domain rules turned into features; text or
   categorical embeddings.
3. **Model family and objective:** linear → GBM → specialized models. Try a loss that
   matches the metric (e.g., focal loss or class weights for PR-AUC, quantile loss for
   intervals).
4. **Hyperparameters:** run a *batch* search (e.g., Optuna with a fixed trial budget,
   inside one run) and log it as a single experiment. Don't hand-tune one parameter per run.
5. **Ensembling and stacking:** last, and only if the gain is worth the operational cost.

**Explore versus exploit.** Mostly make incremental changes from the current best. About
every 5th run, try a **bold** idea: a different representation, a different model
family, or a reformulated target. Greedy hill-climbing on its own gets stuck in local
optima.

**Use evidence to pick ideas.** Base choices on error analysis of the current best
(where it fails, by slice), on feature importance, on the rejected list (don't retry
something without a new angle), and on method scouting.

**Method scouting.** When starting out, or on a plateau, look up how others solved
similar problems: papers, well-regarded competition write-ups, library documentation.
Add the promising ones as ideas, with `--source` set to where each came from. Judge
credibility: reproducible, similar data regime, not a leaderboard trick tied to one dataset.

## 6. Plateau playbook

When `state` shows PLATEAU (no keep in `patience` runs), change strategy rather than
grinding on:
1. **Ablate the kept changes.** Remove each recent keep one at a time. Some were probably
   noise that happened to pass the bar, and taking them out simplifies the model.
2. **Redo the error analysis** on the current best. Look at the 50 worst errors and the
   worst slices. New features usually come from here.
3. **Move up a layer** in §5 (for example, from hyperparameters back to data and features).
4. **Scout methods** (§5) and add three to five ideas.
5. **Question the ceiling.** Label noise or missing signal may cap performance. Estimate
   it (e.g., agreement between labelers, or the performance of an oracle-feature upper
   bound) and report it.
6. If two strategy changes both plateau, **stop**. You've found the practical ceiling
   under this charter. Say so, and recommend what would move it (new data, a relabel, a
   different target).

## 7. Crashes and timeouts

- Trivial bugs (typos, imports, shapes): fix and rerun. This still counts as the same idea.
- Out of memory or a timeout: try a smaller variant once, or log a timeout and move on.
- Conceptually broken ideas: `labbook.py log --status crash`, then move on.
- Three crashes in a row: stop exploring and check the environment (disk, GPU, data
  access, credentials). Don't burn the budget on a broken machine.

## 8. Integrity rules (anti-gaming)

An autonomous optimizer will find any shortcut to a better number. These rules keep the
number meaningful:
- **Never edit locked files:** the evaluator, the metric, the splits, data preparation,
  the holdout. `labbook.py` fingerprints them and discards results if they change. If the
  evaluator has a genuine bug, stop and tell the human.
- Never train on validation or holdout rows, tune on the holdout, or drop "hard" rows
  from validation.
- Features must be available at prediction time. Suspect any gain larger than about five
  times the typical gain: run the leakage scan and check the new feature's timing
  *before* keeping it.
- Guardrails are not optional. A run that doesn't report a guardrail metric is discarded.
- Don't relax `min_delta` mid-run to let a change through.

## 9. Stopping, confirmation, and the holdout

**Stop** when any of these happens:
- the budget is exhausted
- the success bar from the charter is met (then do a short final polish)
- the plateau playbook is exhausted
- the lock integrity check fails
- something outside the charter is needed.

**Confirmation.** After N comparisons, the best validation score is optimistically
biased, because you picked the maximum of many noisy draws. So before declaring a winner:
1. Rerun the top 2–3 candidates with **new seeds** (and a different fold or time window
   if you have one).
2. Choose the final model by the confirmation results, preferring the simpler one on ties.
3. Score the **holdout once**: `labbook.py holdout --metric X`. The lab book refuses a
   second scoring unless it is forced with a stated reason. Report the holdout number as
   the expected performance.

## 10. Running long jobs in an agent harness

- For runs longer than about two minutes, launch the harness as a background command
  with a timeout if your environment supports it, and continue once it finishes. Don't
  sit polling. Otherwise, run it with a hard timeout.
- For multi-hour sessions, the lab book is the memory. If the context is summarized or the
  session restarts, `labbook.py state` restores everything needed to continue.
- Never stop or kill processes you didn't start (e.g. a blanket `taskkill /IM python.exe`
  or `pkill python`). Other jobs may share the machine. Stop only your own PIDs.
- **Parallelism** (optional, when sub-agents or git worktrees are available): run independent
  ideas in separate git worktrees. Only the orchestrating agent writes to the lab book,
  and it applies the keep rule to each result against the current best.
- Keep it cheap. Sample data for early idea screening, and confirm promising ideas at full
  scale. Watch warehouse scan costs and GPU hours against the budget.

## 11. Final deliverable

1. `labbook.py report > experiment_report.md` gives the improvement path, all runs,
   hypotheses, and ideas.
2. Write an executive summary on top of it (see `communication.md`):
   - the best model versus the baseline, **with the holdout number** and its CI (from `eval_report.py`)
   - what drove the gains (the kept changes, ideally confirmed by ablation)
   - what was tried and didn't work (this saves the next team weeks)
   - the practical ceiling and what would move it
   - recommended next steps.
3. If the model will ship: a model card, a monitoring plan, and the Phase 5 checklist in SKILL.md.
